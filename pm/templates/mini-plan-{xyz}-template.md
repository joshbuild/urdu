# Mini-plan — {Xyz}

> **Template usage.** **Assign the next `mp##` handle from `pm/mini-plans.md` first, then name the file** — a slug chosen before a handle is the one that gets written without one. Copy this file to `pm/mini-plans/mp##-{slug}.md` (replace `{xyz}`/`{Xyz}`/`{slug}` with the mini-plan's kebab-case name and `mp##` with the assigned handle — e.g. `mp07-onboarding-polish.md`). **The handle leads the filename; there is no un-prefixed form** — the `mini-plans/` directory already encodes the type, so drop the `mini-plan-` and `-template` infixes entirely (never `mini-plan-onboarding-polish.md`, never a bare `onboarding-polish.md`). Handle width is natural, two-digit minimum (`mp01` … `mp108`); existing handles are never re-padded. Full rule: `pm/pm-glossary.md` §4. Then fill each section, deleting the italic prompt as you answer it. Reach for a **mini-plan** when you have **N bundled tasks worth sequencing** but **no single vision** — a vision-less execution container (the discriminator vs a *feature*, which owns a north-star; vs an *issue*, which is one problem with a diagnosis arc). If it grows a vision, promote it to a feature. Register it as a row in `pm/mini-plans.md` and give it an `mp##` handle. Cross-cutting decisions promote to `pm/DECISIONS.md` as usual. See `pm/pm-glossary.md` §1 for the work-type boundaries.
